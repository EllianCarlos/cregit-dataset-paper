## The batch 2 instance: batch3L and the power-off rule

- `census-batch3L-wait.service` checks every 60 s and starts `census-batch3L.service` when
  census-batch2 is no longer active, or when batch 2 has no unstarted project left AND runs at
  most 15 projects (20 slots minus the 5 L). Status line: `/run/census-batch3L-wait.status`,
  also in batch3L/live/progress.txt.
- Each census has its own finalize (copy to `batch2/final/` resp. `batch3L/final/`, size and
  SHA256SUMS checks, DONE). A finalize powers the instance off (stop, not terminate) only if the
  OTHER census has finalized: its `final/DONE` is in S3 and its units are not active
  (`/usr/local/bin/census-other-done`). Each writes its DONE before it asks, so the second one
  powers off. The old guards stay: no power-off if the check fails, the census ran < 1 h, or
  `/home/ec2-user/NO_SHUTDOWN` exists.
- Tested 03:31 UTC with `--decide-only` and `--dry-run` (batch2/dryrun/, batch3L/dryrun/): no
  power-off while the other runs; "would power off" when the other's DONE exists.
- Backups of the edited scripts: `/usr/local/bin/census-batch2-live.orig-20261009`,
  `/usr/local/bin/census-batch2-finalize.orig-20261009`.

## Spot instances

Units (installed by `scripts/spot-install-<a|b>.sh`, generated by `scripts/gen-spot-install.sh`):
`census-b3@<part>` (one per part), `census-b3-upload.timer` (every minute: each project whose final
ledger row is done/done-dirty goes to `batch3/<a|b>/done/<project>/` with Parquet, .validated,
state json and logs, a ledger snapshot; sizes are listed back and compared, then `OK` is written),
`census-b3-live.timer` (10 min), `census-b3-watch` (IMDSv2 `spot/instance-action` every 5 s; on a
notice: STOP in every part's ctp clone, INTERRUPTED + ledgers to live/, one upload pass),
`census-b3-finalize` (waits until no part is active; then copies all parts to
`batch3/<a|b>/final/<instance-id>/`, checks, DONE; writes `batch3/<a|b>/final/DONE` only when every
project of the batch has done/OK; then `shutdown -h`, and the instance TERMINATES because it was
launched with shutdown behavior terminate. After a real spot notice it copies nothing).

Watcher test (fake notice, census not stopped): `echo '{...}' > /run/census-fake-spot-notice` as
root on the instance; it writes `live/INTERRUPTED.test`, ledger.*.test.jsonl and
/run/census-STOP.test.<part>. Done on batch3a at 03:52 UTC: ok.

## Stop

Run as root on the instance via SSM (`I=<id> scripts/ssm.sh <script>`), with a one-line script:

- batch 2: `touch /home/ec2-user/ctp/STOP` (running projects finish, then finalize).
- batch3L: `touch /home/ec2-user/ctp-b3L/STOP` (before it started, this also holds the waiter).
- spot a: `for d in /data[0-9]*; do touch $d/ctp/STOP; done` (every part); spot b:
  `touch /home/ec2-user/ctp/STOP`. Finalize then copies and the instance terminates; add
  `touch /home/ec2-user/NO_SHUTDOWN` first to keep it. A later `restart_spot.sh` runs the rest.
- Keep any instance up after its census: `touch /home/ec2-user/NO_SHUTDOWN`.

## Restart a spot instance after an interruption

    ~/s3-work/ec2-batch3/restart_spot.sh a      # or b

It refuses if `batch3/<a|b>/final/DONE` exists or an instance of that batch still runs; launches

over m6id.24xlarge c6id.32xlarge r6id.24xlarge m6idn.24xlarge r6idn.24xlarge i4i.24xlarge
m5d.24xlarge m5dn.24xlarge in all 4 AZs; launch template `cregit-census-batch3-spot` ${RUNNER_LAUNCH_TEMPLATE}
with the batch 3 AMI; `TYPES="..."` narrows the list; `FULL=1` = m6id.24xlarge from the plain AL2023
AMI with the full setup); makes the layout (a: one XFS per disk; b: RAID0 of all disks); copies the
inputs (sha256 checked); installs the scripts; runs the identity check (the census does not start
unless CHECK OK); then `census-b3-start`, whose `census-b3-prep` writes each part's run manifest =
its share of `manifest.batch3<a|b>.tsv` minus every project with `done/<project>/OK`, with a fresh
ctp ledger. Instances launched are appended to `instances.txt`.

## A/B test: 4 filesystems (a) versus one RAID0 (b)

Why: on batch 2, step 2 waits on cross-directory `rename()`, serialised per filesystem
(`s_vfs_rename_mutex`); see `s7-run/ec2-load-20261009.md`. a splits the work over 4 filesystems
with 5 workers each; b keeps one RAID0 with 20 workers. Both get alternate rows in u order, so the
S/M mix is alike. Compare:

    mkdir -p ab && aws s3 sync s3://${RUNNER_BUCKET}/batch3/a/done/ ab/a/ --exclude '*.parquet'
    aws s3 sync s3://${RUNNER_BUCKET}/batch3/b/done/ ab/b/ --exclude '*.parquet'
    python3 -I ab_compare.py ab/a ab/b

It prints per side the projects, step-2 commits/s (commitsProcessed / step 2 seconds; median and
pooled), median project minutes and projects/hour (projects / (last end - first start)).
Interruptions make wall time gaps; compare within one instance's run where possible. Run 2 has
a and b on the same type (i4i.24xlarge, 6 disks of 3750 GB, 96 vCPU, 768 GiB), so a has 6 parts.
If a later restart puts a and b on different types (see `instances.txt`), the comparison is weaker:
compare only rows of the same type. Memory: the smallest type in the list, c6id.32xlarge, has 256
GiB; batch 2 used about 70 GiB at 20 workers, so `--min-free-mem-gb 24` and `--memory-limit 16GB`
fit (inferred). m5d/m5dn disks are 900 GB: with `--disk-floor-gb 500` a part on one of them has
about 400 GB before it stops starting projects (enough for S/M, inferred).
